# 0009 · `/pdlc-feature` 每个阶段交给全新子代理

- **状态**：Accepted
- **日期**：2026-10-12
- **作者**：kanfu-panda
- **关系**：建立在 ADR 0008（状态推进交给脚本）之上；不改目标项目契约

---

## 1. 背景

`/pdlc-feature` 在一个会话里从 PRD 一路做到评审。到写实现时，上下文里留着写测试时的全部推理：哪些用例是凑出来的、哪里本想多测一点。
模型很容易顺着这些去迁就，而不是只对着测试和设计干活；会话越往后上下文越长，后面阶段的注意力也越分散。

ADR 0008 的测试指纹能拦住「改测试」，拦不住「按自己知道的实现思路去写测试」。隔离上下文是在源头上少一些这种机会。

## 2. 决策

有子代理工具（Claude Code 的 Task / Agent）时，阶段二～五各交给一个全新的 general-purpose 子代理，一个接一个执行：

- **主会话保留**：需求澄清（要问人）、功能ID分配、阶段一（创建状态文件）、阶段六最终报告，以及每阶段之后的核对
- **子代理执行 `/pdlc-feature` 自己的那一节**，读同一份 SKILL.md，用同一个 `scripts/pdlc-advance.sh` 收尾
- **主会话读状态文件核对**（`last_phase_result.stage` / `ok` / `current_stage`），不信子代理的回报；不对就停，可续跑
- **子代理出错重派一次**，仍不行就停；不在主会话里替它做完（那样隔离就没了）
- **没有子代理工具**时照旧在主会话里依次执行，最终报告写明「各阶段未隔离执行」

## 3. 考虑过的方案

| 方案 | 结论 |
|---|---|
| 子代理调用单独的 `/pdlc-design`、`/pdlc-tdd`、`/pdlc-implement`、`/pdlc-review` | 不选。实测子代理能调到插件 skill，但单独命令与 `/pdlc-feature` 内联阶段并不等价：评审阶段写 CHANGELOG、`--lite` 下跳过设计对照等只在后者里。换成单独命令等于悄悄换了行为 |
| 加开关（如 `--isolated`），默认不派子代理 | 不选。隔离是更好的默认，没有理由让用户记一个开关；没有子代理工具时自动回退 |
| 阶段一也交给子代理 | 不选。需求澄清要问人，子代理不能和用户对话 |
| 各阶段并行 | 不可行。后一阶段要读前一阶段的产物 |

## 4. 代价

- 每个子代理都要重新读 SKILL.md 和上游产物，token 比内联略多。`--lite` 实测一轮约 1.6 美元、3.4 分钟（Claude，评测场景 `feature-lite`）。
- 子代理看不到对话，产出语言由主会话写进派发提示词。
- 评测 Claude 臂默认放行 `Task Agent`，否则只验到回退路径。
